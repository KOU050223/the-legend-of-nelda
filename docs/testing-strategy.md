# Testing Strategy

## 0. このドキュメントの目的

本ドキュメントは、**The Legend of Nelda プロダクト全体に共通するテスト方針**を定義する。

Phase 1 の1人用ボス戦PoCだけでなく、今後追加する以下の機能も対象とする。

- 1人用ボス戦PoC
- 見ざる / 聞かざる / 言わざるへの3人分割
- 3クライアントのリアルタイム同期
- 視線推定 / 顔向き推定
- 発話検知
- 音声ルーティング
- 観客用神視点UI
- 現実世界への覚醒イベント
- センサー / IoT / 外部デバイス連携

テストの具体的な書き方・実行方法は [`testing-guide.md`](./testing-guide.md) に分離する。
本ドキュメントは「何をどこまでテストするか」の方針のみを扱う。

個別Phaseの具体的なテストケースは、必要に応じて別ドキュメントへ分離する。

例:

```text
docs/
├─ testing-strategy.md
├─ testing-guide.md
├─ single-player-poc-spec.md
└─ tests/
   ├─ phase1-single-player-test-spec.md
   ├─ phase2-three-player-test-spec.md
   └─ phase3-real-world-integration-test-spec.md
```

---

# 1. テストの目的

本プロジェクトでテストを書く主目的は、テスト件数やカバレッジ率そのものを増やすことではない。

以下を目的とする。

1. **デバッグ時間を減らす**
2. **仕様変更による既存機能の破壊を早期検知する**
3. **Phase 2以降のリファクタリングを安全に行う**
4. **複数人開発で変更の影響範囲を把握しやすくする**
5. **本番デモ直前の致命的な不具合を減らす**
6. **一度修正したバグを再発させない**

特に本プロジェクトでは、Phase 1 の1人用ロジックを後から3人協力用へ分解するため、**ゲームロジックに対する回帰テストを重要視する。**

---

# 2. 基本方針

## 2.1 ロジックは自動テストする

以下のような、入力と出力が明確な処理は原則として自動テストを書く。

- State遷移
- 入力受付判定
- ダメージ計算
- HP / SLEEPINESS管理
- 攻撃成功 / 失敗判定
- 攻撃シーケンス
- タイマー / 制限時間
- 3人同期時のゲーム状態
- Cue配信先の制御
- 勝利 / 敗北条件

---

## 2.2 見た目・気持ちよさはプレイテストする

以下は無理に自動テストしない。

- アニメーションが自然か
- SEが気持ちいいか
- カメラシェイクが強すぎないか
- ボス攻撃が見切りやすいか
- UIが分かりやすいか
- 1戦のテンポが良いか
- 三猿のコミュニケーションが実際に面白いか
- 観客から見て状況が理解できるか

これらは、**人間によるプレイテスト / デモテスト**で確認する。

---

## 2.3 実装Issueの中でテストまで完了させる

テスト実装を最後にまとめて行わない。

ロジックを追加・変更するIssueは原則として、

> **実装 + 対応するテスト**

までを同じIssueのDefinition of Doneに含める。

例:

```text
ボス技「枕薙ぎ払い」を実装

実装
- 攻撃方向
- 回避判定
- 被弾判定
- 反撃Window

テスト
- 右攻撃 → 左回避で成功
- 左攻撃 → 右回避で成功
- 同方向回避で失敗
- 早押しでTOO EARLY
- 被弾でSLEEPINESS増加
- 成功後にCOUNTER_WINDOWへ遷移
```

# 3. テストレベル

本プロジェクトでは主に以下の4段階を使う。

## 3.1 Unit Test

小さなロジック単位をテストする。

対象例:

- 入力受付時間判定
- Damage計算
- SLEEPINESS加算
- 攻撃方向判定
- タイマー
- 発話違反判定
- Cue配信条件

Unit Testでは、可能な限り描画・音声・ネットワーク・実時間に依存させない。

---

## 3.2 Integration Test

複数のロジックを組み合わせた動作を確認する。

対象例:

```text
TELEGRAPH
↓
ATTACK
↓
入力判定
↓
COUNTER_WINDOW
↓
DAMAGE
↓
IDLE
```

または、

```text
Boss Attack Event
↓
Audio Cue Event
↓
対象Playerへ配信
```

など。

---

## 3.3 E2E / Scenario Test

ゲームの主要フローを通しで確認する。

例:

- チュートリアル開始
- 枕薙ぎ払い
- あくび衝撃波
- ふかふか布団
- 本戦
- Boss HP 0
- 勝利State

Phase 2以降では、

- 3人が同一Roomへ接続
- 役割ごとの情報を受信
- 共同操作
- ボス撃破

までを対象とする。

E2EはUnit Testより本数を少なくし、主要シナリオへ絞る。

---

## 3.4 Playtest / Manual Test

人間が実際に遊んで評価する。

対象例:

- 難易度
- 面白さ
- 予兆の分かりやすさ
- 3人協力の必然性
- コミュニケーション事故の面白さ
- UI / UX
- 演出
- 会場デモでの理解しやすさ

自動テストがすべて通っていても、Playtestで問題があれば仕様・実装を調整する。

---

# 4. 境界値テスト

時間判定を多く利用するため、**境界値テストを重要視する。**

例として回避受付時間が以下の場合、

```text
-0.60 sec ～ +0.10 sec
```

少なくとも次を確認する。

| 入力時刻 | 期待結果 |
|---:|---|
| -0.61 | TOO EARLY / 失敗 |
| -0.60 | 成功 |
| 0.00 | 成功 |
| +0.10 | 成功 |
| +0.11 | 遅すぎる / 失敗 |

同様に、

- Boss HP 1 / 0
- SLEEPINESS 99 / 100
- Counter Window直前 / 直後
- Room人数 2 / 3

など、仕様の境界は重点的に確認する。

---

# 5. 時間依存処理のテスト

ゲーム内時間をそのまま実時間で待つテストは極力避ける。

タイマー・入力受付・攻撃タイミングなどは、可能な限り**時間ソースを差し替え可能な構造**にする。

推奨イメージ:

```text
GameClock
├─ RealClock
└─ FakeClock (test)
```

テストではFakeClockを進めて、

- 0.6秒前
- 着弾時
- 0.1秒後

などを即座に再現できる状態を目指す。

これによりテスト実行時間とFlaky Testを減らす。

---

# 6. Random処理のテスト

ボス攻撃や左右方向などのランダム要素は、テスト時に結果を固定できるようにする。

例:

```text
RandomProvider
├─ ProductionRandom
└─ FixedRandom (test)
```

「たまたま右攻撃が出たからテスト成功」のようなテストは禁止する。

---

# 7. 視覚・音情報の分離テスト

本プロジェクトでは、後の三猿分割のために以下を分離する。

```text
Game Logic
├─ Visual Cue
├─ Audio Cue
├─ Weak Point Cue
└─ Input
```

Phase 1の時点から以下を確認する。

- Visual Cueを無効化しても攻撃ロジックが動く
- Audio Cueを無効化しても攻撃ロジックが動く
- Cue表示処理がBoss HP等のゲーム状態を書き換えない
- Cueイベントを個別に購読できる

この分離を維持することで、Phase 2では

```text
見ざる → Audio Cue
聞かざる → Visual Cue
言わざる → 特殊情報
```

のような配信制御を安全に追加できるようにする。

---

# 8. ネットワーク / 3人協力のテスト方針

Phase 2以降で実施する。

最低限以下を検証する。

## 同期

- 3クライアントでBoss HPが一致する
- Player入力が正しいGame Stateへ反映される
- 攻撃開始時刻が大きくずれない
- Roleごとの情報が正しいClientへ届く

## 権限制御

例:

- 見ざるに禁止されたVisual Cueが届かない
- 聞かざるに禁止されたAudio Cueが届かない
- 他Role専用操作を実行できない

## 切断

- 1人が切断した場合
- 再接続した場合
- Roomに3人揃っていない場合

の挙動を定義し、テストする。

---

# 9. センサー / AI / Human Interface系のテスト方針

対象例:

- 視線推定
- 顔向き推定
- 発話検知
- MediaPipe
- マイク入力
- DeviceMotion
- ジャイロ

これらは実センサーに依存したテストだけにしない。

センサー処理を、

```text
Raw Sensor
↓
Sensor Adapter
↓
Game Logic
```

に分離し、Game Logic側にはテスト用の疑似値を渡せるようにする。

例:

```text
GazeInput = CENTER
SpeechDetected = true
DeviceTilt = LEFT
```

など。

実機による確認はManual Testとして別途行う。

---

# 10. 外部デバイス / 現実干渉のテスト方針

将来実装する覚醒イベントでは、

```text
Game Clear
↓
Wake Event
↓
External Device
```

を直接密結合しない。

Wake Event発火までを自動テストし、実デバイス部分はAdapter経由にする。

例:

```text
WakeOutput
├─ MockWakeOutput
├─ SmartphoneOutput
├─ IoTOutput
└─ WearableOutput
```

自動テストではMockWakeOutputを使用し、

- 勝利時に1回だけWake Eventが送信される
- 敗北時には送信されない
- 重複送信されない

などを確認する。

実際に人を起こせるかどうかはManual / Demo Testとして確認する。

---

# 11. UIテスト方針

UIの見た目そのものを細かく自動テストしすぎない。

自動テストするもの:

- Boss HP変更時にHUD更新イベントが発生する
- SLEEPINESS変更時に表示値が更新される
- Stateに応じて必要なUIが表示される
- Roleによって非表示にすべきUIが表示されない

Manual Testで確認するもの:

- 見やすさ
- レイアウト
- フォントサイズ
- 演出の強さ
- 観客からの理解しやすさ

---

# 12. バグ修正時のルール

バグを修正する場合、可能な限り以下の手順を取る。

1. バグを再現するテストを書く
2. そのテストが失敗することを確認する
3. バグを修正する
4. テストが成功することを確認する
5. 既存テストもすべて通す

つまり、

> **Bug Fix = Regression Test追加**

を原則とする。

見た目・実機依存など、自動テストが現実的でない場合はIssue / PRへ再現手順を残す。

---

# 13. CI方針

CIはGitHub Actions等を利用し、少なくともPull Request時に実行する。

基本フロー:

```text
Pull Request
↓
Install
↓
Lint / Format Check
↓
Unit Test
↓
Integration Test
↓
Build Check
↓
Merge
```

原則として、必須テストが失敗している状態ではマージしない。

CI環境で実行が難しい実機 / センサー / IoT系テストは必須CIから分離する。

---

# 14. Flaky Testを避ける

以下のような不安定なテストを避ける。

- 実時間のsleepに依存
- ランダム結果に依存
- ネットワーク速度に依存
- 実マイク入力に依存
- 実カメラ入力に依存
- テスト実行順序に依存

Flaky Testが発生した場合、単純に再実行して放置せず原因を修正する。

---

# 15. Test Double

必要に応じて以下を利用する。

- Mock
- Stub
- Fake
- Spy

特に以下は差し替え可能にしておくとテストしやすい。

```text
Clock
Random
Network
Audio Output
Visual Output
Sensor Input
Wake Output
```

---

# 16. テストケース命名

テスト名から、

> **何をしたら、どうなるべきか**

が分かる名前を推奨する。

例:

```text
rightPillowAttack_leftDodge_shouldSucceed
rightPillowAttack_rightDodge_shouldHit
sleepinessReaches100_shouldLose
visualCueDisabled_attackLogicShouldStillWork
```

採用技術の命名規則に合わせて変更してよい。

---

# 17. Phaseごとのテスト仕様

このドキュメントではプロダクト全体の方針のみ定義する。

具体的なテストケースはPhaseごとに別途作成する。

## Phase 1

予定:

```text
docs/tests/phase1-single-player-test-spec.md
```

対象:

- State Machine
- 4操作
- 3ボス技
- 入力受付境界値
- HP / SLEEPINESS
- チュートリアル
- 勝敗
- Cue分離

## Phase 2

予定:

```text
docs/tests/phase2-three-player-test-spec.md
```

対象:

- Role分配
- 3人同期
- Cue配信制御
- 操作権限
- 通信経路
- 切断 / 再接続

## Phase 3以降

必要に応じて、

- センサー
- 現実世界連携
- 観客UI

などのテスト仕様を追加する。

# 18. Definition of Done

ロジックを伴うIssueは、原則として以下を満たした時にDoneとする。

- [ ] 実装が完了している
- [ ] 正常系テストがある
- [ ] 主要な異常系テストがある
- [ ] 境界値がある場合は境界値テストがある
- [ ] 既存テストがすべて成功する
- [ ] CIが成功する
- [ ] 必要に応じてManual Testを実施している
- [ ] 仕様変更がある場合は関連ドキュメントを更新している

UI / VFX / SEなど自動テストが適さないIssueでは、自動テストを無理に追加せずManual Testの確認内容を明記する。

---

# 19. Pull Request時の最低確認項目

PR作成者は最低限以下を確認する。

```text
- [ ] 変更内容に対応するテストを追加 / 更新した
- [ ] ローカルでテストが通る
- [ ] CIが通る
- [ ] 既存機能を壊していない
- [ ] 必要なManual Testを実施した
- [ ] 仕様変更があればdocsを更新した
```

---

# 20. カバレッジについて

Phase 1の段階では、コードカバレッジ率そのものをKPIにしない。

重要なのは、

- 壊れると影響が大きいロジック
- 境界値
- 状態遷移
- 過去に発生したバグ

がテストされていること。

必要になった段階でカバレッジ計測を導入するが、

> **カバレッジ100%を目的にはしない。**

---

# 21. 優先順位

時間が限られるハッカソン開発では、以下の順でテストを優先する。

1. 戦闘State / 勝敗条件
2. 入力受付 / 境界値
3. Boss HP / SLEEPINESS
4. ボス攻撃ロジック
5. 3人同期 / Role制御
6. 現実干渉イベント
7. UIの状態制御
8. 演出

「見た目の細かい部分を自動テストするために、コアゲーム実装が遅れる」状態は避ける。

---

# 22. この戦略の最終目的

本プロジェクトでは、Phase 1で作った1人用ゲームを後から大きく分解・拡張する。

そのため、テストは単なる品質保証ではなく、

> **安心してゲーム構造を壊し、作り直し、三猿3人協力へ進化させるための安全網**

として扱う。

テストを書くこと自体を目的にせず、**開発速度とデモ成功率を上げるために必要な箇所へ重点的に導入する。**
