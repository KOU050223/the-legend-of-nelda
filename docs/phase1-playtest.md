Issue #14 の最終確認用。自動化できる通し進行は

## 2026-09-14: deterministic scenario check

Fake Clockで各攻撃の受付開始に防御し、通常反撃は0.8秒後、布団反撃は0.3秒後に
入力した。これは予兆を確認してから行動する成功中心のテンポを再現する。

| Case | Result |
| --- | --- |
| E2E-001 全成功 | 最終ふかふか布団（step 11）で勝利。60〜90秒の目標内 |
| E2E-002 全失敗 | SLEEPINESS 100で `PLAYER_LOSE`。終了後に次の攻撃は開始しない |
| E2E-003 枕を1回失敗 | SLEEPINESS +6（補助付きチュートリアルの半減値）の後、最終布団まで進み勝利 |
| E2E-004 布団の反撃を見送り | 大ダウンなしで次の枕へ進む。SLEEPINESSは増えない |

既定のHP、ダメージ、眠気、受付時間、IDLE間隔は変更しない。全成功で最終布団まで到達し、
1回の軽い失敗後も勝利でき、連続失敗は終了状態へ入るため、調整の根拠を満たしている。

## 2026-09-14: browser layout check

1280×720のDesktop Chrome相当で、以下を確認した。

- Boss HP、SLEEPINESS、チュートリアル補助、操作説明、Effectsパネルが同時に読める。
- 枕の予兆では、ボス横の枕と中央の `← / → DODGE` が読める。
- Audio Cue / Visual Cue は別々のチェックボックスで無効化でき、各強度は0.0〜2.0で設定できる。
- 勝利・敗北のResultは通常HUDより前面に表示され、Restartで戦闘へ戻る。

画面確認だけでは音のタイミング、初見の理不尽さ、反撃の手触り、3人協力への分解可能性は
判断できない。次の人間プレイテストで確認する。

## 3人プレイテスト手順

各参加者は、初見1戦・成功を目指す1戦・意図的に連打する1戦を行う。各戦の開始からResultの
Restart表示までを計測し、以下を記録する。

| Item | 判定・記録 |
| --- | --- |
| MANUAL-001 | 枕の左右を、補助なしで読み取れたか |
| MANUAL-002 | あくびの吸気から無音への切替を、ガードの手掛かりにできたか |
| MANUAL-003 | 布団を通常技より大技と判断できたか |
| MANUAL-004 | 失敗理由を説明でき、受付を理不尽と感じなかったか |
| MANUAL-005 | 連打だけで安定して突破できなかったか |
| MANUAL-006 | 回避・ガード後の反撃を気持ちよいと感じたか |
| MANUAL-007 | 成功中心の計測値が60〜90秒か |
| MANUAL-008 | HUDとEvent表示が操作・予兆を隠さないか |
| MANUAL-009 | SE/VFXの既定強度が邪魔でなく、設定変更が効くか |
| MANUAL-010 | 視覚・聴覚・判断・操作を別の人へ渡せそうか。渡すなら何が不足するか |

参加者ごとの失敗回数、結果、所要時間、自由記述をIssue #14へ追記する。3人が完了するまでは、
このドキュメントのブラウザ確認を人間プレイテストの代替として扱わない。

## Phase 2への持ち越し

- `ATTACK_VISUAL_CUE` と `ATTACK_AUDIO_CUE` は既に別イベントで、Effectsパネルも個別に切替できる。配信先をプレイヤーごとに変える土台はある。
- 判断と操作は同じキーボード入力に集約されている。三猿分割では、入力を役割ごとのAdapterへ分離し、誰がどのActionを許可されるかをサーバーまたは共有Stateで管理する必要がある。
- 音の無音区間はAudio Outputに閉じている。聞かざる向けの情報制限では、音量のON/OFFではなく、Cue単位のルーティングが必要になる。
