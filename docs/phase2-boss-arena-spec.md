## 2. 広さの決め方

`phase2-gameplay-spec.md` §2 の

> 3人で走り回って、離れたり集合したりできる広めのボスアリーナ

を、**具体的な攻撃が成立する距離**へ落とす。現在の移動速度は 4 units/秒
（`PlayerCharacter` の `DEFAULT_SPEED`）。

| 距離 | 値 | 所要（4 units/秒） | 何のための値か |
| --- | --- | --- | --- |
| 中心 → 端 | 24 | 6.0秒 | ブルーライト照射（§9.2）から逃げ続けられる長さ |
| 端 → 端 | 48 | 12.0秒 | 散ったあと合流し直せる長さ。これ以上広げると移動待ちが増える |
| スポーン → ボス | 18 | 4.5秒 | 開幕に密着していない距離 |
| 装置 → 隣の装置 | 29.4 | 7.4秒 | 結界（§11.1）で「間に合うか」の緊張が出る距離 |
| 中心 → 最寄りの安全地帯 | 11 | 2.8秒 | 睡眠時間圧縮フィールド（§9.3）の退避 |
| 最遠地点 → 最寄りの安全地帯 | 17.3 | 4.3秒 | **#58 の予兆時間の下限**。これより短い予兆にすると端にいる人が詰む |

半径を変えるときは `ARENA_RADIUS` の1箇所を直せば、床・岩の壁・木立・装置・安全地帯が
すべて追従する。**数値はプレイテストで調整する前提**で、この表を更新する。

## 3. 座標

Three.js 標準の座標系（Y = Up）。カメラは +Z 側から原点を見るため、**スポーン側が +Z、奥が -Z**。
角度は `Math.atan2(z, x)` の向きで、+X を 0度とする。

### スポーン地点

| | x | z | ボスまでの距離 |
| --- | --- | --- | --- |
| 1 | -4 | 18 | 18.4 |
| 2 | 0 | 18 | 18.0 |
| 3 | 4 | 18 | 18.4 |

3人とも +Z 側へ置く。`facingRotationY` の規約では rotationY = 0 が -Z 向きなので、
**初期回転を与えなくても3人ともボスを向く**。横並びなのは「まず合流している状態から散る」導入にするため
（`phase2-gameplay-spec.md` §3）。

### 装置・安全地帯・祭壇

`ringLayout()` で供給する。位置そのものが意味を持つので `angleJitter: 0` を渡して等間隔にする
（木・岩・草は既定の揺らぎのままばらけさせる）。

| 種類 | 半径 | 角度 | 座標 |
| --- | --- | --- | --- |
| 装置 1 | 17 | 0° | (17.00, 0.00) |
| 装置 2 | 17 | 120° | (-8.50, 14.72) |
| 装置 3 | 17 | 240° | (-8.50, -14.72) |
| 安全地帯 1 | 11 | 60° | (5.50, 9.53) |
| 安全地帯 2 | 11 | 180° | (-11.00, 0.00) |
| 安全地帯 3 | 11 | 300° | (5.50, -9.53) |
| 祭壇 | 20 | 270° | (0.00, -20.00) |
| ボス | 0 | — | (0.00, 0.00) |

安全地帯は装置から60度ずらしてある。同じ角度に重ねると片側だけが混み合い、
「散らす」という攻撃の役割（§9.3）が薄れるため。安全地帯1つの広さは `SAFE_ZONE_RADIUS` = 3.5。

アンカーは位置に加えて `rotationY`（アリーナ中心を向く向き）を持つ。
規約は `facingRotationY` と共通で、[`arena.test.ts`](../src/game/arena/arena.test.ts) で突き合わせてある。

## 4. 境界

**当たり判定は持たせない。** 移動そのものを円の中へ丸める
（[`clampToBounds`](../src/game/movement/movement.ts)）。

- 半径だけを丸めて角度は保つ。壁へ斜めに押し当てたとき接線方向の成分が残り、
  **止まらずに壁沿いへ滑る**。逃げ回る攻撃で壁に張り付くと理不尽になるため。
- 入力の有無によらずクランプする。「返り値は必ず範囲内」という不変条件にしておくと、
  呼び出し側が経路ごとに気を配らなくてよい。
- `bounds` を渡さなければ従来どおり制限しない。Phase 1 の呼び出しには影響しない。

見た目の側では、プレイ可能範囲のすぐ外側（`ARENA_RADIUS + 2.5` 〜 `+ 5.5`）に岩を密に並べて
「どこで止まるか」を示す。木立はさらに外側にしか置かない。当たり判定のない木をアリーナ内部に置くと
中を素通りできてしまい、境界が壁として読めなくなるため。

**地面の広さはプレイ可能範囲とは別の値**（`GROUND_SIZE`）。地面をプレイ可能範囲ぴったりにすると、
境界を示す岩や木の足元から地面が消えて宙に浮く。

## 5. `?scene=world` の扱い（決定）

### 決定

**dev限定のまま維持する。** 本番ビルドでは引き続き Phase 1 の戦闘シーンだけが出る
（[`src/app/scene-mode.ts`](../src/app/scene-mode.ts)）。

### 理由

現時点のアリーナにはボスも戦闘もHPも無い。本番の既定シーンに昇格させると、
デプロイ先で**動いている Phase 1 のデモが「歩けるだけの画面」に置き換わる**。
Issue #54 が要求しているのは昇格そのものではなく「昇格経路が決まっていること」なので、
ここで決めて記録する。

### 昇格の条件

次の2つが揃った時点で本番の既定シーンへ切り替える。

1. #56 3人共通の基本アクション（移動・攻撃・回避・インタラクト）が動く
2. #58 堀大輔のボス基盤と通常攻撃が乗り、**1人で勝ち負けがつく**

`phase2_mvp_missing_issues.md` §3 の「A〜E の5件で1人で堀大輔と戦って勝ち負けがつくループが閉じる」に対応する。

### 昇格のときに触るファイル

| ファイル | 変更内容 |
| --- | --- |
| `src/app/scene-mode.ts` | `import.meta.env.DEV` のガードを外し、既定を combat から arena へ入れ替える |
| `src/app/App.tsx` | `isWorldSceneRequested()` の分岐を反転させ、戦闘一式の起動条件を戦闘シーン側へ移す |
| `src/rendering/scene/GameScene.tsx` | 背景色・ライトの既定をアリーナ側へ入れ替える |

3ファイルとも分岐は1箇所ずつで、切り替え自体は小さい。判定を1つの純粋関数へ寄せる整理は、
**実際に切り替える時**に一緒に行う（今やると使われない抽象だけが増える）。
